## ADR (WH(Y) Statement format)

**In the context of** Iris as a multi-entity knowledge-graph application
with a growing feature surface — collections, sets, packages, diagrams,
elements, bookmarks, Ask AI, search, knowledge graph, admin tools —
where a new user landing on the app currently sees a login screen
followed by an unadorned dashboard, and the only in-app help is a
keyboard-shortcuts page at `/help`,

**facing** GitHub issue #15 requesting "a user guide documented from
the end-to-end tests, with screenshots of all the screens", "included
in the menu", and "with a navigation bar",

**we decided for** a **markdown-backed user guide at `/guide`** with
nine hand-written sections (Getting Started, Dashboard, Collections
& Sets, Packages & Diagrams, Knowledge Graph, Search, Ask AI,
Bookmarks, Admin), a left-hand in-guide navigation bar, rendered from
`.md` source imported via Vite's `?raw` query through `marked` and
`DOMPurify` (both already in `frontend/package.json`). Screenshots are
produced by a Playwright spec (`tests/screenshots/generate.spec.ts`)
run on demand via a new `npm run screenshots` script; PNGs are written
to `frontend/static/guide/` and committed so that Render serves them
without needing Playwright at build time on the deployed environment,

**and neglected** (a) auto-generating guide prose from BDD `.feature`
files — Gherkin steps are implementation-oriented and read poorly as
end-user prose, and feature files change with test refactors in ways
that wouldn't serve readers; (b) a single-page README-style guide —
issue #15 explicitly asks for a navigation bar, which a single page
doesn't meaningfully provide; (c) converting the existing `/help`
route into the user guide — `/help` is a shortcuts reference (a
different audience and a different reading pattern), and coexisting
with `/guide` is cleaner than reshaping a focused page; (d) using
`mdsvex` to compile markdown at build time — adds a new dependency
and a new build step when `marked` already renders markdown elsewhere
in the app (`SetQA.svelte`) and DOMPurify already sanitises HTML per
protocol #7,

**to achieve** a user guide that ships as pure static markdown +
PNGs — easy to edit, easy to review in pull requests, easy to serve
— with a route structure and rendering stack identical to the
existing pattern (`/help` is a Svelte page; `/guide` will be too;
both are framework-native),

**accepting that** screenshots are produced manually via
`npm run screenshots` rather than on every deploy (the user agreed
this was acceptable — screenshots tend to "drift" less rapidly than
UI, and committing them keeps CI fast); accepting that content is
hand-written prose and must be maintained alongside feature changes
(mitigated by the small section count and by the guide being
immediately visible in-app); accepting that each section is a
standalone `.md` file imported via `?raw`, which means renaming or
reorganising sections touches both the `.md` file and the guide's nav
config.
